# RFC 9700 checklist for an authorization-code-only OIDC provider (OP side)

Pinned 2026-11-18. Sources and sha256: `docs/spec-pins/spec-pins.json` (ids rfc9700, rfc6749, rfc7636, rfc9207, rfc8725, rfc9068). Requirement text is paraphrased; section numbers are those of the RFC. "Applies" = applies to eidbridge acting as OP / authorization server. Client-side-only duties are marked "no" or "partly" with the OP-side consequence in notes. Last column is intentionally empty.

Assumption used for "applies": code flow only, ID tokens issued, access tokens may be JWT, Smart-ID is the user authentication method (no passwords), refresh tokens and dynamic client registration undecided (marked "partly" where they decide the answer).

## B. RFC 9700 section 4 (attacks and countermeasures) and RFC 6749 / 7636 pieces they reference

| RFC 9700 section | Requirement (paraphrase) | Applies (OP side)? | Notes | eidbridge anchor |
|---|---|---|---|---|
| 4.1.3 | AS MUST ensure the redirect URI in the request equals a registered one by simple string comparison (RFC 3986 6.2.1); only `localhost` port variation for native apps allowed. | yes | Redirect URI validation attack class (4.1.1, 4.1.2). Do not allow wildcards, prefix or subdomain matching. | ADR-008: Authorize parameters, errors before validation |
| 4.1.3 | Servers hosting redirect URIs MUST NOT expose open redirectors. | partly | Client-hosted; for OP's own pages see 4.11. | ADR-008: Authorize parameters, errors before validation |
| 4.1.3 | Servers MAY append an arbitrary fragment (for example `#_`) to Location redirects to stop fragment re-attachment. | no | Optional, implicit-flow oriented. | ADR-008: Authorize parameters, errors before validation |
| 4.1.3 | If origin/integrity of the request is verified (JAR RFC 9101, PAR RFC 9126 with client auth), AS MAY trust the redirect URI without further checks. | no | Optional; not planned. | ADR-008: Authorize parameters, errors before validation |
| 4.2.4 | The authorization endpoint page and response-handling page SHOULD NOT include third-party resources or links to external sites. | yes | Applies to login/QR/consent pages. | 4.2.4 | (Countermeasure, non-normative list) suppress `Referer` with `Referrer-Policy: no-referrer`; prefer code response type; bind code to client or PKCE; consider form_post. | yes | Set `Referrer-Policy: no-referrer` on all OP HTML. `form_post` response mode is optional. | Threat model: UI injection and framing |
| 4.2.4 / RFC 6749 4.1.2 | Authorization codes MUST be invalidated after first use at the token endpoint; on a second redemption attempt AS SHOULD revoke tokens issued from that code. | yes | Atomic single-use consume in the code store; revoke-on-replay recommended. | ADR-008: Authorization code and Replay |

| 4.4.2 | Clients using two or more AS MUST prevent mix-up. | no | Client duty; OP supports by emitting `iss` (RFC 9207). | ADR-008: `iss` row and discovery |
| 4.4.2.1 | AS sends its issuer identifier in the authorization response; client compares and aborts on mismatch; `iss` evaluated per RFC 9207. | yes | OP side: always emit `iss` (section C). | ADR-008: `iss` row and discovery |
| 4.4.2.2 | Alternative defense: distinct redirect URI per issuer; SHOULD be used only if `iss` is not available. | no | Client-side. | ADR-008: `iss` row and discovery |
| 4.5.3.1 | PKCE is the main countermeasure against authorization code injection and also protects codes of public clients. | yes | See 2.1.1 rows. | ADR-008: Authorize request |
| 4.5.3.2 | If `nonce` is used instead of PKCE the client MUST validate `nonce` in the ID token from the token endpoint and disregard all tokens until it succeeds. | partly | OP side: always echo `nonce` into the ID token. | 4.6.1 | Access token injection is detectable only with OIDC (`at_hash`, `nonce`), via ID token in authorization response. | no | Code-only: no tokens in the authorization response. | ADR-008: Authorize request |
| 4.7.1 | Clients MUST confirm the AS supports PKCE before relying on it for CSRF; otherwise `state` or `nonce`. `state` carrying data MUST be integrity-protected. | 4.8.2 | AS supporting PKCE MUST check whether a challenge was in the authorization request, bind it to the code, and reject a token request with `code_verifier` when no challenge was bound. | yes | Same as 2.1.1 downgrade row. | 4.9.3 | Resource server MUST NOT store or transfer access tokens in plaintext; sender-constraint and audience restriction SHOULD be used. | partly | Applies to eidbridge's UserInfo/RS role: store only hashes of opaque tokens. | ADR-008: RFC 9700 gap table (deviation or not applicable) |
| 4.10 | AS SHOULD issue sender-constrained and audience-restricted access tokens. | partly | See 2.2.1 and 2.3. | ADR-008: RFC 9700 gap table (deviation or not applicable) |
| 4.11.2 | AS MUST NOT automatically redirect on invalid `client_id`/`redirect_uri` combination (RFC 6749 4.1.2.1: show an error page instead). | yes | Error page, no redirect, for unregistered or mismatching redirect URIs. | ADR-008: Authorize parameters, errors before validation |
| 4.11.2 | AS MUST always authenticate the user before redirecting (except silent authentication) and decide whether the redirect URI is trusted; SHOULD auto-redirect only to trusted URIs. | yes | OIDC `prompt=none` is the silent-auth exception. | 4.12 | AS redirecting a request that may contain credentials MUST NOT use HTTP 307; SHOULD use 303. | yes | Post-login redirects: 303 (or 302 only for GET). Smart-ID flow has no password but forms may still POST identity data. | ADR-008: Authorize parameters, errors before validation |
| 4.13 | Reverse proxy MUST sanitize inbound security-relevant headers; proxy-to-app link MUST be protected against eavesdropping, injection and replay. | partly | Deployment: trusted-proxy handling of `X-Forwarded-*`/client-cert headers. | ADR-003: Endpoints and proxies |
| 4.14.2 | Refresh tokens: risk-based issuance; bound to consented scope/resources; public clients need replay detection (sender-constraint or rotation); SHOULD expire on inactivity; integrity of grant-encoding values MUST be ensured. | partly | Only if refresh tokens are issued; otherwise document "none issued". | ADR-008: RFC 9700 gap table (deviation or not applicable) |

## C. RFC 9207 (issuer identification), OP/AS requirements

## D. RFC 8725 (JWT BCP) items touching an OP issuing ID tokens / JWT access tokens

| RFC 8725 section | Requirement (paraphrase) | Applies (OP side)? | Notes | eidbridge anchor |
|---|---|---|---|---|
| 3.1 | Libraries must take an allow-list of algorithms, use no others, make `alg`/`enc` match the operation, and use each key with exactly one algorithm. | yes | Applies to signing keys and to validation of client assertions / `id_token_hint`. Pin `alg` per key (`kid`). | ADR-007: Algorithms |
| 3.2 | Use only cryptographically current algorithms; design for cryptographic agility; avoid `none` unless the JWT is protected otherwise; ECDSA via deterministic nonces (RFC 6979) is SHOULD. | yes | Never issue `alg: none`. | 3.3 | All cryptographic operations in a JWT (including nested) MUST be validated; reject the whole JWT on any failure. | yes | When the OP consumes JWTs (client assertions, request objects, `id_token_hint`). | ADR-007: Algorithms |

| 3.6 | SHOULD NOT compress data before encryption. | no | No JWE planned. | ADR-007: Algorithms |
| 3.7 | UTF-8 only for JSON in headers and claims. | yes | Applies to JWT encoding/decoding (Go `encoding/json` default). | ADR-007: Algorithms |

| 3.11 | Use explicit typing (`typ`) for new JWT kinds, media-type form `application/<x>+jwt`, `application/` prefix omitted in the value; explicit typing is RECOMMENDED for new uses. | yes | JWT access tokens: `typ` `at+jwt` (RFC 9068, below). | ADR-008: RFC 9700 gap table (deviation or not applicable) |
