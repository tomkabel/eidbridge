# Personal data flow

This page lists every piece of personal data eidbridge receives, holds, emits and discards, so an integrator can use it in their own records of processing and DPIA. It describes the code on the `feat/full-build` branch. It is not legal advice and makes no role determination for your deployment; see [legal stance](legal.md). Security controls are in [security](security.md).

## Roles

- **Integrator (operator)**: runs the bridge and the client application, decides why logins happen. Usually the controller.
- **eID scheme operator** (for example SK ID Solutions for Smart-ID and Mobile-ID): processes the authentication under its own agreement with the integrator.
- **Project authors**: receive nothing. There is no telemetry, no update check and no crash upload (NFR-004). Anyone hosting the bridge for third parties takes on their own data-protection role and obligations.

## Sequence

~~~mermaid
sequenceDiagram
    box Device of the user
        participant B as Browser
        participant A as eID app or wallet
    end
    box Integrator
        participant C as Client app or IdP
    end
    box Operator host
        participant E as eidbridge
    end
    box Scheme operator
        participant S as eID service
    end
    B->>C: open the service
    C->>B: redirect to /authorize (state, nonce, PKCE)
    B->>E: front channel - authorize, login page, flow cookie
    E->>S: create session (challenge, RP identity, identifier only in notification flows)
    S->>A: authentication request
    A->>S: user confirms on the device
    E->>S: poll session status
    S->>E: signed result with certificate
    E->>E: verify, derive claims, discard certificate and secrets
    E->>B: redirect with one-use code (iss, state)
    B->>C: code
    C->>E: back channel - token request (code, client auth, PKCE)
    E->>C: ID token and sealed access token
    C->>E: userinfo with access token
    E->>C: allow-listed claims
~~~

## Field inventory

"Held" is always process memory: nothing below is written to disk or a database. Lifetimes are maxima.

| Field | Purpose | Source | Held where | Lifetime in the bridge | Leaves the bridge to | Logged |
|---|---|---|---|---|---|---|
| National identity code (`PNOEE-…` serial number) | Subject derivation; optional `personal_code` claim | Verified certificate; in notification flows also typed by the user | Flow entry, then claim set | Until code exchange or 60 s code expiry | Only the `personal_code` claim to an allow-listed client; otherwise only as the HMAC `sub` | Never (redacted at the sink) |
| Identifier typed in notification mode | Address the push | Login form | Flow entry (`[]byte`), rate-limit key as HMAC under a separate process key | Until verification or terminal state; HMAC key bucket until idle refill | eID service (request path) | Never |
| Phone number and personal code (Mobile-ID) | Address the request; the certificate identity must equal the typed code and country | Login form; checked locally (+372/+370 E.164, code checksum) before any request | Mobile-ID session; rate-limit key as HMAC under a separate process key | Reference dropped at verification or terminal state (Go strings are not zeroed; the heap is reclaimed by the collector) | Mobile-ID service (`phoneNumber`, `nationalIdentityNumber`) | Never |
| Given name, family name | `given_name`, `family_name` with the `profile` scope | Verified certificate Subject (Smart-ID, Mobile-ID, ID-card through Web eID) or wallet PID | Claim set | Until exchange or 60 s | Client (ID token, userinfo) | Never |
| Country | `country` claim | Verified certificate | Claim set | Until exchange or 60 s | Client | Never |
| Birth date (EUDI wallet only) | `birthdate` with the `profile` scope, if the wallet discloses it | Verified PID presentation | Claim set | Until exchange or 60 s | Client | Never |
| PID personal identifier and issuing country (EUDI wallet) | Subject derivation, `country` claim | Verified PID presentation | Claim set | Until exchange or 60 s | Only as the HMAC `sub` (or `personal_code` to allow-listed clients) | Never |
| Authentication certificate, signature, Web eID token, wallet credential | Verification only | eID service, the user's browser (Web eID) or wallet | Verification call | Discarded when verification ends | Never | Never |
| `rpChallenge`, `sessionSecret`, callback verifier, Mobile-ID hash and verification code, Web eID nonce, wallet nonce | Protocol binding | Generated by the bridge or returned by the service | Flow entry (`[]byte`, cleared on terminal state) | Until verification or terminal state | `rpChallenge`/nonce to the service or device only; `sessionSecret` never leaves the backend | Never |
| Authorization code | One-use delivery | Generated | Code store, as SHA-256 only, with the claim set | 60 s, or atomic consume at exchange; expired entries swept every second | Client (redirect) | Never |
| Code tombstone and token family | Replay revocation | Generated | Reserved code-store slot | Access-token lifetime plus skew | Never | Never |
| Access token | userinfo | Sealed (AES-256-GCM) by the bridge | Not stored; the client holds it | ≤ 5 minutes; invalid after restart | Client | Never |
| ID token | Login result | Signed by the bridge | Not stored | Lifetime ≤ access-token lifetime | Client | Never |
| `sub`, `previous_sub` | Stable account link | HMAC-SHA256 under K_sub (ADR-007) | Claim set | Until exchange or 60 s | Client | Never |
| Flow cookie | Bind the flow to one browser | Generated: random binding token, creation time, `client_id`, `redirect_uri`, `state` | Browser | Until the flow's absolute deadline; cleared on every terminal state | — | Never |
| Remember-method cookie (opt-in) | Preselect a method | User's choice | Browser | 30 days; ignored when the method is disabled | — | Never |
| Client IP address | Rate limiting | TCP peer or trusted `X-Forwarded-For` hop | Rate-limit memory, as IPv4 address or IPv6 /64 | Until the bucket is idle and refilled | Never | Never (access log has route and status only) |
| User agent | — | HTTP request | Not read | — | Never | Never |
| EUDI same-device `response_code` | Bind a same-device wallet response to the login browser (OpenID4VP 1.0 §8.2) | Generated by the bridge, sent to the wallet in `redirect_uri` | Flow entry, with the verified claim set held until the browser returns | Until the browser returns with its flow cookie or the flow's deadline | The wallet (which opens it in the browser) | Never |
| Signer identifier (`PNOEE-…`, signing API) | Certificate choice | Integrator request | Request, then the background job that polls the certificate choice | Until the certificate choice is verified or fails (at most the 3-minute session timeout) |  Smart-ID service (request path) | Never |
| Signing certificate (signing API) | Returned to the integrator; checked against the signature | Smart-ID service | Signing job, in memory, bound to one client | Until consumed by one signature request, or 5 minutes (unreadable through the API from then; dropped from memory at the next 30 s sweep, so at most about 5 min 30 s) | The integrator that requested it | Never |
| Digest, display text, signature value (signing API) | Digest relay | Integrator (digest, text); Smart-ID service (signature) | Signing job, in memory | Until the result is delivered once, or 5 minutes (unreadable through the API from then; dropped from memory at the next 30 s sweep, so at most about 5 min 30 s) | Digest and text to the Smart-ID service; signature to the integrator | Never |

## Claims emitted

Every claim the OIDC provider can emit appears here; a test compares this table with `oidc.ClaimNames()`.

| Claim | When |
|---|---|
| `iss`, `aud`, `exp`, `iat` | Always (ID token) |
| `sub` | Always: HMAC, public or pairwise per client |
| `auth_time` | Always; every login is fresh |
| `nonce` | Always (required in the request) |
| `acr` | Always: `demo` in demo mode; otherwise the method URN or the operator mapping (ADR 0003) |
| `amr` | Always: method name |
| `country` | Always |
| `eid_method` | Always |
| `eid_env` | Demo mode only (`demo`) |
| `given_name`, `family_name` | `profile` scope, when the verified evidence carries them |
| `birthdate` | `profile` scope, wallet method only, when disclosed |
| `personal_code` | `personal_code` scope, allow-listed clients only |
| `previous_sub` | During a declared `K_sub` or sector migration, declared clients only |

## Settings that change the flow

| Setting | Effect |
|---|---|
| Client `sub_mode` (`public` or `pairwise`) and `sector_id` | Whether clients can link one user across services (public: yes, by design) |
| Client `personal_code_allowed` | Whether the national code itself can reach that client |
| `EIDBRIDGE_SMARTID_FLOWS=…,notification` | Users type an identifier; account existence becomes observable to an attacker who can push (disclosed residual risk) |
| `EIDBRIDGE_METHODS` containing `mobileid` | Users type a phone number and personal code; both go to the Mobile-ID service, and account existence is observable in the same way as Smart-ID notification |
| `EIDBRIDGE_METHODS` containing `webeid` | The browser sends the card's authentication certificate in the token; the bridge contacts the card CA's OCSP responder with the certificate serial number |
| `EIDBRIDGE_METHODS` containing `eudi` | The wallet posts the PID presentation (including the holder key) to the bridge; the bridge fetches the status list from the issuer's status host, which learns that a list was fetched but not which entry |
| `EIDBRIDGE_SIGNING_ENABLED=true` | Integrators send a signer's personal code to the bridge, which forwards it to Smart-ID and returns the signing certificate (it contains the personal code) and the signature; no document reaches the bridge (docs/signing.md) |
| `EIDBRIDGE_TRUSTED_PROXIES` | Which address the rate limiter sees |
| `EIDBRIDGE_LOG_LEVEL=debug` | More events; the same redaction (NFR-002) |
| Reverse proxy access logs | Outside the bridge: the operator must keep query strings (codes, callback values) out of them |

## What the bridge cannot delete

Tokens and claims already delivered to a client are outside the bridge. Deleting bridge state does not retract them. The client's own account store, sessions and logs are the integrator's responsibility.
