# Maintenance runbook: upstream API, TLS and key changes

How eidbridge tracks and responds to upstream changes and key incidents. Support policy: fixes ship in the latest minor release; TLS pin and CA fixes are backported one minor release if it is maintained, subject to maintainer capacity. No SLA.

## Sources to watch

| Source | What changes there | Pin id in `docs/spec-pins/spec-pins.json` |
|---|---|---|
| Smart-ID RP API docs and changelog (`sk-eid.github.io/smart-id-documentation`) | API versions, fields, verification rules | `smartid-rp-api-v3-*` |
| Smart-ID environments page | Hosts, scheme names, demo RP identity | `smartid-environments` |
| SK certificate repository (`c.sk.ee`, skidsolutions.eu) | New issuing CAs, demo CA rotation | — (record fingerprints in `trust/<env>/README.md`) |
| Scheme operator technical announcements | TLS policy, certificate renewals | — |
| Mobile-ID REST API repository, Web eID specifications, OpenID4VP/HAIP/SD-JWT VC specifications | Later methods | added with each method |

The weekly review is manual: compare each pinned page's hash, record new hashes with the date, and mark machine findings unreviewed until a maintainer reads them. Nothing runs as a background monitor.

## Change types

| Change | What breaks | How it is detected | Files to update | Release |
|---|---|---|---|---|
| RP API minor version or field change | Parsing or verification fails closed; logins end `failed(unknown_end_result)` or `verification_failed` | Nightly live test, user reports, changelog | `docs/spec-pins/`, `internal/smartid`, fixtures, negative tests | Minor |
| TLS policy change (cipher removal) | Handshakes fail | Nightly `scripts/pin-check.sh`, startup errors | Usually none; Go defaults; check `internal/tlspin` | Patch |
| RP API server certificate renewal | Pin mismatch if the SPKI changed | `pin-check.sh` (nightly), actionable startup error naming observed and expected pins | `trust/<env>/smartid-tls-pins.txt`, release notes with new pins | Patch, backport |
| Issuing CA added or rotated | `verification_failed` (chain) for new users | Live test, user reports | `trust/<env>/smartid-auth-ca/`, README fingerprints | Patch, backport |
| Demo key or demo CA rotation | Demo logins fail; production unaffected | Nightly live test | `trust/demo/`, `internal/config/demo.go` | Patch |

## Nightly workflow

`.github/workflows/live-demo.yml` runs `scripts/pin-check.sh demo` and `EIDBRIDGE_LIVE=1 go test -run TestLive ./...` against the public demo (using SK's automated testing interface, no human). On failure it opens one issue labelled `upstream-change` (or comments on the open one) with the run link and step names only. A run with the `bogus_pin` input simulates a pin mismatch to test the issue path. **Status:** committed, not yet run on GitHub (running it is a repository action for the owner).

Each upstream change gets an issue from `.github/ISSUE_TEMPLATE/upstream-change.md` and a `CHANGELOG.md` "Upstream compatibility" entry.

## Incident reason-code matrix

| Incident | Detect | Contain | Drain | Rotate | Recover | Notify |
|---|---|---|---|---|---|---|
| User refusal (`refused`) | Flow log reason code | None needed | — | — | User starts again | — |
| Abuse: push spam or enumeration | Rising `rate_limited` and per-target denials | Lower per-target/per-IP buckets, disable notification flow | — | — | Re-enable with tighter limits | Affected users if identifiable through the scheme operator |
| Upstream outage (`upstream_error`, `retries_exhausted`) | Flow reason codes, status page, `eidbridge doctor` | Nothing to contain; show the generic message | — | — | Wait; flows expire | Clients if prolonged |
| Stale pin or CA (`verification_failed`, TLS errors) | Pin mismatch error, nightly check | Stage the new pin or CA next to the old one | — | Update pin or CA, restart | Verify with `trust show` and a demo login | Operators via release notes |
| Signing-key compromise | Key file exposure, unexpected JWKS | `eidbridge keys revoke <kid>` | Restart immediately (drops all access tokens) | Replacement key is generated by `revoke` | Clients refresh JWKS and re-authenticate users | Clients at once; review legal notification timing yourself |
| K_sub compromise | Key file exposure | Treat as a privacy incident (codes are enumerable) | — | New K_sub version plus `EIDBRIDGE_SUB_MIGRATION` window with `previous_sub` | Retire the old version after clients relink | Clients; review legal notification yourself |

The operator decides legal notification timing and applicability; the project does not prescribe it.

## Key recovery drill

Run both procedures on a staging instance at least once per release:

1. **Planned rotation**: note the active `kid` (`eidbridge keys list`), `eidbridge keys rotate RS256`, restart; an ID token issued before the rotation still verifies against JWKS until its expiry (test `TestRetiredKeysSurviveRestart`); the old key disappears after `not_after`.
2. **Emergency revocation**: `eidbridge keys revoke <kid>`, restart; the key is gone from JWKS at once, a replacement is active, earlier access tokens fail at userinfo (tests `TestEmergencyRevocationDropsKeyFromJWKS`, `TestCompromisedKeyDroppedImmediately`).
3. **K_sub rotation**: add version 2 to the K_sub file, set `current: 2` and a migration window for each client; declared clients receive `previous_sub` (test `TestSubKeyVersionMigration`); an undeclared change refuses to start (`TestSubKeyOrModeChangeNeedsMigration`).

Record the date, commit and outcome of each drill in the release deviation table. **Drill status:** the automated tests above pass; a drill on a deployed staging instance is NOT RUN.
